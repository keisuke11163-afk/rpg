## 1. 方針

| # | 方針 | 理由 |
|---|---|---|
| 1 | **ルールの中核はブラウザの機能とPhaserに依存させない。依存していないことを、コンパイルと自動検査の両方で守る** | 描画なしでテストとシミュレーションを大量に回すため（開発計画書3.1） |
| 2 | **コンテンツ（データ）を、コードとは別のパッケージにする** | 本体を変えずにコンテンツを追加・変更できるようにするため（本仕様書10.1） |
| 3 | 使う道具は最小限にし、**バージョンを固定する** | 再現できるビルドのため。AIが生成するコードが、環境の違いで壊れないようにする |
| 4 | 全ての検査（型・リント・テスト・データの検証・ビルド）を、**1つのコマンドと自動テストの仕組み（CI）で実行できる**ようにする | ブランチごとの完了の手順（MVP実装単位2.2）を、毎回同じ方法で確かめるため |

| Vite | 8系（8.3.5） | 開発サーバー・ビルド | — |

| Playwright | **この環境に入っている版（1.63.0）を使う**（別の版を入れない） | ゲームが起動するかの確認・画面の撮影 | テストの道具（@playwright/test）を使う場合も1.63系に揃える |

### 2.1 Phaser 4 と Phaser 3 の選択

| 選択肢 | メリット | デメリット |
|---|---|---|
| **Phaser 4.2系（推奨）** | 現在の安定版（4.0.0は2026年4月、4.2.1は2026年7月）。今後も更新が続く | 3系よりも新しいため、AIの学習データ・解説記事が少ない |
| Phaser 3.90 | 情報が多く、AIのコード生成に慣れた書き方が多い | 2025年5月が最後の版で、更新が止まっている |

**推奨は4.2系**。長く開発を続けるゲームなので、更新が止まった版は選ばない。AIの慣れの問題は、Phaserを使う部分を表示層に閉じ込めて薄く保つことで抑える（ルールの中核はPhaserを使わない）。

## 3. リポジトリの構成

```
rpg/
├─ docs/                      仕様書・計画書（既存）
│   ├─ spec/
│   └─ plan/
├─ packages/
│   ├─ core/                  ルールの中核（タグ・効果・ダメージ・状態異常・ゲージ・ツリー・アイテムの生成・セーブのモデル）
│   │   ├─ src/
│   │   └─ test/
│   ├─ content/               コンテンツのデータ（JSON）と、その検証
│   │   ├─ data/              tags/ effects/ items/ affixes/ uniques/ skills/ jobs/ boards/ enemies/ drops/ areas/ …
│   │   ├─ text/              表示の文章（ja.json）
│   │   └─ test/              データの検証・相互作用の回帰テスト
│   └─ game/                  Phaserを使う表示層（画面・入力・音・UI）
│       ├─ src/
│       └─ assets/placeholder/ 仮素材（必要な場合だけ。基本は実行時に図形から作る）
├─ tools/
│   └─ sim/                   DPSシミュレーター（コマンドで実行する）
├─ .github/workflows/         自動テストの仕組み（CI）
├─ package.json               ワークスペースの全体
├─ pnpm-workspace.yaml
└─ tsconfig.base.json
```

### 3.1 パッケージの依存の規則【正式】

```
game ──→ core
  └────→ content ──→ core
tools/sim ──→ core, content
core ──→ （zod だけ）
```

| 規則 | 守り方 |
|---|---|
| core はブラウザの機能を使わない | core の TypeScript の設定で、ブラウザの型（DOM）を読み込まない → 使うとコンパイルの誤りになる |
| core は Phaser・game・content を参照しない | リントの設定で参照を禁止する。わざと参照したときに検査が失敗することを、U-01の完了の条件にする |
| content はデータとスキーマの読み込みだけ | ゲームの処理は書かない |
| データの形は core のスキーマで決める | content のデータは、core のスキーマで検証する |

## 4. 実行するコマンド（予定）

| コマンド | 内容 |
|---|---|
| `pnpm dev` | 開発サーバーを起動し、ブラウザでゲームを動かす |
| `pnpm build` | 本番用のビルド |
| `pnpm typecheck` | 全パッケージの型の検査 |
| `pnpm lint` | リント（パッケージ間の参照の制限を含む） |
| `pnpm test` | 自動テスト（core・content） |
| `pnpm validate:data` | データの検証（ID参照・値の範囲・乗算の出どころ）と、仮値・仮実装の一覧の出力 |
| `pnpm sim` | DPSシミュレーター（U-05以降） |
| `pnpm check` | 上の検査をすべて順に実行する（**ブランチを完了させる前に必ず実行する**） |
| `pnpm smoke` | Playwrightでゲームを起動し、画面が出ることを確かめる（撮影も行う） |

## 5. 主な設定

| 項目 | 設定 |
|---|---|
| TypeScript | `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、ESモジュール、**`skipLibCheck: true`**（12章：Phaser 4.2.1とZod 4の型の定義ファイルの誤りを避けるため） |
| Phaser | `pixelArt: true`、`roundPixels: true` を明示する（Phaser 4では `roundPixels` の初期値が `false` になったため） |
| Vite | Phaserを別のファイルに分けて出力する（Phaserが500kBを超えるため） |
| 型の安全 | `any` を使わない（リントで禁止） |
| 名前 | コードの名前は英語。データのIDは英大文字とハイフン（例：`UNQ-003`）。表示の文章は `text/ja.json` に分ける（将来の多言語化のため） |
| コメント | 日本語でよい。仮実装には `// 仮実装: 〇〇で置き換える（単位U-xx）` と書く（MVP実装単位2.1） |
| 乱数 | core の中で `Math.random` を使わない（シード付きの乱数だけを使う。リントで禁止） |
| 時間 | core の中で実時間（`Date.now` など）を使わない。時間は固定の時間刻みで受け取る |

## 7. 自動テストの仕組み（CI）

- GitHub Actions で、`develop`・`main` への push と、プルリクエストのたびに `pnpm check` を実行する
- pnpm のキャッシュを使って、実行時間を短くする
- **リポジトリの設定（ユーザーにお願いすること）**：GitHub の画面で、`main` と `develop` を保護し、「CIが通らないとマージできない」「force push を禁止する」設定をおすすめします。この設定はリポジトリの管理画面で行うもので、こちらからは変更しません

## 8. データ・素材・セーブ

| 項目 | 方針 |
|---|---|
| データの置き方 | 種類ごとのフォルダに、JSONのファイルを置く（開発計画書6.2）。仮値には `"provisional": true` を付ける |
| データの読み込み | ゲームの起動時に読み込み、core のスキーマで検証する。開発中は、データを変えると自動で読み直す |
| 仮素材 | 基本は、実行時に図形からテクスチャを作る（画像のファイルを作らずに済む）。**スプライトのキーとアニメーションの定義はデータにして**、本素材に替えても変わらないようにする（補助仕様書2章） |
| セーブの保存先 | 「保存先」を差し替えられる形にする。開発中（ブラウザ）は IndexedDB、デスクトップ版はファイル |
| セーブの形式 | JSON。版の番号を持つ。読み込む前に、元のデータを残してから移行する（開発計画書 R-08） |

## 10. Gitの運用

| 項目 | 規則 |
|---|---|
| `main` | 安定版。直接は開発しない。**ユーザーの承認なしにマージしない** |
| `develop` | 開発中の統合ブランチ。各機能のブランチは、ここから作る |
| `feature/機能名` | 機能ごとの開発ブランチ（MVP実装単位の表のブランチ名を使う） |
| `fix/修正内容` | バグの修正ブランチ |
| マージ | 機能のブランチが完了したら、`develop` へのマージを提案する。マージは、マージコミットを残す方法で行う（履歴を書き換えない） |
| 禁止すること | 既存のブランチの削除、force push、履歴の書き換え |
| コミットのメッセージ | 先頭に種類を付ける（`feat:` 機能、`fix:` 修正、`docs:` 文書、`test:` テスト、`chore:` その他）。本文は日本語でよい |
| リモートへの push | 作業したブランチは、作業の区切りごとに push する（作業の環境が一時的なものなので、作業を失わないため） |

## 11. U-01 `feature/project-setup` で行う作業（予定）

1. `develop` から `feature/project-setup` を作る
2. ワークスペース（`packages/core`・`packages/content`・`packages/game`・`tools/sim`）を作る
3. TypeScript・リント・整形・Vitest・Vite・Phaser を、2章の版に固定して導入する
4. 3.1の依存の規則を、設定とリントで強制する
5. 空のPhaserの画面（タイトルの文字だけ）を作る
6. `pnpm check` と `pnpm smoke` を用意する
7. GitHub Actions の設定を追加する
8. **完了の条件**：
   - `pnpm check` が全て通る
   - `pnpm dev` で、ブラウザに空の画面が表示される（Playwrightで撮影して確認する）
   - core からわざと Phaser を参照すると、検査が失敗することを確認する（確認した後、その変更は元に戻す）
9. コミットして push し、`develop` へのマージを提案する

## 12. 互換性の確認の結果（2026-11-04）

作業用の一時フォルダ（リポジトリの外）に2章の版を入れ、実際に確かめた。詳細は `docs/review/ステラシジル_v0.2_最終確認.md` の4章。

| 確認 | 結果 | 設定への反映 |
|---|---|---|
| 依存の解決（Phaser 4.2.1・TypeScript 6.0.3・Vite 8.3.5・Vitest 5.1.0・Zod 4.6.7・fast-check 4.10.2・ESLint 10.14.0・typescript-eslint 8.72.1・Prettier 3.9.10） | 衝突なし | 2章の版で固定する |
| テスト・ビルド・ブラウザでの起動 | 全て通る。WebGLで描画される | — |
| Phaser 4.2.1 の型の定義 | 定義ファイル自体に2つの誤り（TypeScript 5.9でも同じ） | `skipLibCheck: true` |
| Zod 4 の型の定義 | DOMの型を読み込まないと `URL` が見つからない | `skipLibCheck: true` |
| 依存の規則の検査 | ルールの中核からのPhaserの参照はリントで、ブラウザの機能の使用は型の検査で、それぞれ失敗する | 3.1のとおり |
| Playwright | この環境の版は1.63.0 | 2章のとおり |
