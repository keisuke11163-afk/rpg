### 1.1 MVPの完成の条件（開発計画書4.1を引き継ぐ）

1. 2つのジョブで、操作の感触が明らかに違う
2. 拾った装備（特にユニーク）がきっかけで、ツリーの取り方を変えたくなる場面がある
3. **深淵の母樹**に、まったく違う3つ以上のビルドで勝てる
4. 振り直しとロードアウトで、ビルドを試す・戻すが苦にならない
5. ボスの周回に意味がある
6. **3つ目のジョブを、ゲームの本体を変えずに、データとルールフックだけで追加できる構造になっている**（拡張性の確認）

## 2. 実装の単位の決め方

| 原則 | 内容 |
|---|---|
| 1単位＝1ブランチ | `feature/〇〇` を `develop` から作り、完了したら `develop` へのマージを提案する |
| 単位の大きさ | 完了の条件を**自動テストか、短い手動の確認**で判断できる大きさ。目安は数日分の作業 |
| 縦に切る | 「画面だけ」「計算だけ」で終わらせず、可能な限り「動く」状態で完了させる。ただしG1（ルールの中核）は、描画なしで完結させる |
| 仕様との対応 | 各単位は、実装する仕様の節を明記する。仕様にない判断が必要になったら、**その場で決めずに一覧にして報告する** |

### 2.1 仮実装と正式実装の区別

| 区分 | 意味 | 印の付け方 |
|---|---|---|
| **正式実装** | 仕様どおりに作り、テストで守る。後から作り直さない | — |
| **仮値** | 仕組みは正式だが、数値はバランス調整で変わる | データに `"provisional": true`。仮値の一覧を自動で出す（開発計画書 T17） |
| **仮素材** | 図形の画像・仮の効果音。後で本素材に差し替える | 素材のフォルダを `placeholder/` に分ける。スプライトのキーは本素材と共通 |
| **仮実装** | 後で作り直す前提の、間に合わせの実装（例：G2の時点の、ファイルに書いた敵の配置） | コードに `// 仮実装: 〇〇で置き換える（単位U-xx）` と書き、一覧を自動で出す。**仮実装を残したまま、その置き換え先の単位を完了にしない** |
| **開発用の機能** | デバッグ表示・チート（Lvの変更など） | 開発版のビルドでだけ有効。製品版のビルドには入れない |

### 2.2 各単位を完了させる手順（毎回）

1. 型の検査・リント・自動テスト・データの検証・ビルドを実行する
2. 動作を確認する（単位ごとの「動作確認」の欄。必要なら画面の撮影）
3. 変更の内容を整理する（実装した仕様の節、仮値・仮実装の一覧、見つかった仕様の疑問）
4. コミットする
5. `develop` へのマージを提案する（`main` へのマージは、ユーザーの承認なしに行わない）

