### 0.2 レビューのルール

- 仕様書を唯一の基準資料として扱う。一般的なゲームの慣例で、曖昧な部分を埋めることはしない
- 問題は「問題点」と「修正案」に分けて書く。修正案は**提案**であり、承認されるまで原文には反映しない
- 修正案に複数の選択肢がある場合は、推奨案に「推奨」と書く。決めるのはユーザーである
- 仕様書に定義がないがMVPに必要なものは、本書では**作らない**。「追加仕様が必要」として9章に挙げる

### 0.3 深刻度の判定基準

| 深刻度 | 本書での判定基準 |
|---|---|
| **Critical** | ゲームの中核となる計算・状態が実装できない。または、仕様どおりに作ると重大なバランス崩壊や不正な状態が起きる |
| **High** | 実装前に解決が必要。関係するシステムの実装を始めると手戻りが大きい。または、局所的だが明確な矛盾がある |
| **Medium** | MVPの範囲外のシステムに関係する。または、実装中・テスト中に決めても手戻りが小さい |
| **Low** | 表記の揺れ、細かな数値の不一致、品質を上げるための改善案 |

「矛盾」でも、影響が局所的で直すのが簡単なものはHigh以下にしている（判定の理由は各項目に書く）。

## 1. 仕様書レビュー結果

### 1.1 総評

- **設計の骨格は実装可能**。星紋タグを共通の言語にする（1.5節）、効果を「タグ＋条件＋効果」で書く（10.1節）という方針は、データ駆動の実装とよく合う。相互作用を「システムを横断する修正値と、ルールを変える処理」の2種類に整理すれば実装できる
- 一方で、**ダメージと状態異常の計算の細部、条件付きで効果が変わる仕組みの評価順序、「基礎性能」などの用語の定義**に穴がある。これらはゲームの中核の計算に関わるので、実装前に決める必要がある（Critical 4件）
- **仕様書は3つのシステムに集中した文書**なので、MVPに必要な周辺の仕様（敵の行動、ダンジョンの構造、町、経済、死亡時の扱いなど）がない。これは仕様書の欠陥というより、作業範囲の違いによるもの。別の文書で定義する必要がある（H-12）

|---|---|
| Critical | 4 |
| High | 13 |
| Medium | 25 |
| Low | 10 |

### 1.3 観点別の所見

#### A. システム間の整合性

| 観点 | 所見 | 関連する項目 |
|---|---|---|
| 装備・星辰盤・職紋盤・流派盤・サブジョブ | 経路（6.0節）ははっきりしている。ただし、**装備や条件によってツリーの状態が変わったときの評価順序と、条件を失ったときの扱い**が決まっていない | C-04 |
| 星紋タグの定義と適用範囲 | タグの一覧はある。ただし、**武器タグの親子関係**（刃の門「剣系（長剣・大剣）」）と、ユニークの効果が**その武器だけに効くのか、全体に効くのか**が決まっていない | H-08、6章 |
| 共鳴紋・残響・遺物・潜在効果・星門・転変ノード | 各仕組みの定義はある。残響の「数値部分は50%」が**代償まで半分にしてしまう**。共鳴紋の「効果+10%」がルール型の輝星にどう効くか不明 | H-08、M-03 |
| ジョブ固有ゲージと技の依存 | 闘志・信念・コンボ点は概ね定義済み。**位相の状態遷移**と**集中の増え方**が曖昧。サブジョブの簡易動作（5.1）は定義済み | H-09、M-23 |
| 武器適性とジョブ | 適性の効果と、サブジョブとの比較方法は定義済み。「適性Cで使えない職技」が未指定。素手の扱いがない | M-11、M-14 |
| ダメージ計算と補正の順序 | 式（2.4）に**技倍率の位置がない**。「次の攻撃に加える」型の追加ダメージの扱いが不明 | H-01 |
| 状態異常・属性変換・CD・リソース | 変換は一方向で整合している。ただし**背誓の「闇属性になる」が聖の変換禁止と矛盾**。状態異常の持続ダメージの総量／毎秒の表記、基準値の範囲、HP・MPの基礎値が未定義 | C-03、H-04、H-11 |

| 観点 | 所見 | 関連する項目 |
|---|---|---|

| 技のコストと威力 | MPの最大値と回復量が未定義なので、コスト（旋風：毎秒12MP、隕星：30MP）が妥当か検証できない | H-04 |

| ユニークの性能と入手難度 | ルール型の効果と潜在効果で、価値が陳腐化しにくい作りになっている。ただし「基礎性能」の定義次第で、盾のガード率が100%を超える | C-01 |

#### C. 実装可能性

| 観点 | 所見 |
|---|---|
| システムの依存関係 | 「タグと効果の仕組み → ダメージ計算 → 戦闘 → ジョブ・スキル／装備 → ツリー」の順に依存している。**効果を評価する仕組みが全ての土台**なので、最初に作る（5章） |
| データとして管理すべき情報 | 装備・詞・ユニーク・技・ジョブ・ノード・状態異常・敵・ドロップ表は全てデータにできる。ルールを変える効果（天極・ユニークの固有効果）は、**名前の付いた処理（ルールフック）を本体で作り、データからはパラメータを付けて参照する**形にする（6章） |
| 共通化できる処理 | 修正値の集計（装備・ノード・ジョブ・一時効果で同じ形）、条件の判定、タグの照合、「休眠」の判定（星門・星渡り・遺物・巡礼で同じ規則にできる。C-04の修正案）、ゲージ（数値・上限・増減の規則をデータにする） |
| 複雑で実装コストが高い部分 | ①約2,000ノードのツリー（星辰盤960＋職紋盤540＋流派盤480）の**コンテンツ量**とUI ②条件付きで効果が変わる仕組みの再評価 ③試し打ちの場（本番とは別の「仮の状態」が必要） ④ロードアウト（装備の実体を参照する） ⑤8方向のドット絵アニメーションの量 |
| 後からの拡張に必要な設計 | IDを固定する、データの版を管理する、セーブデータを移行する仕組み、タグの追加、ルールフックの登録（10章の予約枠を受け入れられる構造） |
| セーブ・ロードで保存すべき情報 | 6.9節に一覧を載せる。特に、**ロードアウトごとのツリーの配置、装備の実体のID、詞片の書庫、討伐証、鍛造負荷、ジョブごとのLv、武器熟練** |
| UIで表示・操作が必要な情報 | タグの一致を光らせる、潜在効果の「？？？」と系統のヒント、休眠ノードの灰色表示、共鳴紋の記号、ゲージの表示（狂王の首飾りや剣舞士のように**ゲージが2つ**になる場合もある）、比較の表示 |

## 2. 修正が必要な項目一覧

> 各項目は「①該当する章・システム／②問題の内容／③なぜ問題か／④影響する他のシステム／⑤推奨する修正案」の順に書く。修正案は全て**承認待ちの提案**であり、仕様書の原文は変更していない。

### 2.1 Critical（4件）

#### C-01 「基礎性能」が何を指すのか定義されていない

| 項目 | 内容 |
|---|---|
| ① 該当箇所 | 2.2（能力値の要求を満たさないと基礎性能-40%）、3.9（強化1段階ごとに基礎性能+5%）、3.11.4（再鍛）、4.7 K09 徒手の極意（副手の基礎性能が2倍） |
| ② 問題 | 「基礎性能」に、盾のガード率・武器の攻撃速度・会心率・射程・基本刻印が含まれるのかが書かれていない |
| ③ なぜ問題か | 含まれるとすると、大盾のガード率70%が強化+10で105%、徒手の極意で140%、小盾50%も徒手で100%になる → **正面からのダメージを完全に無効化できる**（重大なバランス崩壊）。攻撃速度1.40も、強化+10で2.10になる。逆に含まれないとすると、B6（盾の性能を2倍にするビルド）の強さの見積もりが変わる |
| ④ 影響 | 強化、再鍛、能力値の要求、徒手の極意、B6、盾流、円卓の残光、錆鉄の誓約（防いだダメージの量） |
| ⑤ 修正案 | **推奨**：基礎性能を「武器の基礎ダメージ（最小・最大）」と「防具・盾の防具値・回避値・魔障」に限ると明記する。攻撃速度・会心率・ガード率・射程・基本刻印は含めない。徒手の極意の「2倍」も同じ定義にする<br>代替案：ガード率を含める場合は、ガード率の上限（例：90%）を新しく決める |

#### C-02 技・呪文・召喚物の成長の仕組み（技レベル）が定義されていない

| 項目 | 内容 |
|---|---|
| ① 該当箇所 | 3.6（「職技レベル+1／+2」の詞）、5.4（火球の基礎12–20などの固定値）、5.5（召喚物の基礎能力）、8.2（パワーカーブ） |
| ② 問題 | 技レベルの上がり方と、1レベルあたりの効果が、仕様書のどこにも書かれていない。呪文は武器ダメージを使わずに固定の基礎値を持つが、その値が成長する手段がない。召喚物の基礎HP・ダメージと、その成長も定義されていない |
| ③ なぜ問題か | 敵のHPはLv1からLv100で約320倍になる。武器職は、ベースのtier・強化・追加値で基礎値が伸びるので標準DPSに届く（1.2節の検算）。しかし呪文の基礎値が固定だと、加算+400%と乗算×4を合わせても約×20にしかならず、**魔法使い・召喚士は中盤以降に成り立たない**。また、「職技レベル」の詞は効果を持たない |
| ④ 影響 | 魔法使い・召喚士（と、それを含む混成職）、詞の表、8.2節、ビルド例 B3／B4／B5／B7、召喚物の生存（敵のダメージとの比較） |
| ⑤ 修正案 | 選択肢（いずれも仕様の追加なので承認が必要）<br>A（**推奨**）：技レベルの仕組みを定義する（上がり方と、レベルごとの基礎値の表）。仕様書に「職技レベル」の詞がすでにあるので、それとも整合する<br>B：呪文と召喚物の基礎値を、キャラLvに連動させる式を定義する<br>C：呪文用の「追加ダメージ」の詞を新しく作る（武器の追加値と同じ役割） |

#### C-03 状態異常のダメージ計算の定義が不完全

| 項目 | 内容 |
|---|---|
| ① 該当箇所 | 2.4（ダメージ計算）、2.7（状態異常の表と基準値の原則）、9章 V-07、7章 B2 |

## 3. 開発方針と推奨技術スタック

### 3.1 開発方針

| # | 方針 | 理由 |
|---|---|---|
| 1 | **ゲームのルール（計算・状態）と、表示（描画・音・入力）を完全に分ける** | 本作の難しさは相互作用の計算にある。ルールの部分を描画なしで動かせれば、何千通りの組み合わせを自動テストとシミュレーションで確かめられる |
| 2 | **コンテンツは全てデータで持つ**。本体の処理には、汎用の仕組みと、名前の付いたルールフックだけを置く | 約2,000ノード・詞・ユニーク・技を、本体を変えずに追加・変更できるようにする（仕様書10.1節の方針） |
| 3 | **固定の時間刻みで計算する**（描画のフレームレートと分ける）。乱数はシード（種）を指定できるようにする | パリィ（0.18秒）のような精密な判定、再現できるテスト、DPSのシミュレーションに必要 |
| 4 | **入力は「行動」として抽象化する**（例：「技1」「回避」「照準の方向」）。キーとボタンの割り当ては設定データにする | 初期版はキーボード・マウス。後からゲームパッドを足しても、ゲームの処理を変えずに済む |
| 5 | **セーブデータに版の番号を付け、移行の手順を最初から用意する** | ノードのIDを固定する（仕様書10.2）、変更されたノードを無料で振り直す、という運用に必要 |
| 6 | **完全シングルプレイ・取引なし**を前提に、通信と不正対策は作らない | 確定した条件。その分の工数を相互作用の検証に回す |

### 3.3 推奨構成：TypeScript＋Phaser（ルールの部分はエンジンに依存させない）

| 層 | 技術 | 役割 |
|---|---|---|
| ルールの中核（シミュレーション層） | **TypeScript（エンジンに依存しない）** | タグ・効果・修正値の集計、ダメージ、状態異常、ゲージ、ツリー、アイテムの生成、ドロップ、クラフト、セーブデータのモデル。**Phaserを一切参照しない** |
| 表示層 | **Phaser**（開始する時点の安定版を、バージョンを固定して使う） | 描画、アニメーション、カメラ、音、入力の受け取り、UIの画面 |
| データ | JSON（またはYAMLからの変換）＋スキーマによる検証 | 全てのコンテンツの定義。読み込むときに、形・ID参照・値の範囲を検証する |
| マップ | タイルマップエディタの出力（ダンジョンが固定マップに決まった場合。9章 決定事項） | ダンジョンの地形・配置 |
| ビルド・テスト | Vite（開発サーバーとビルド）、Vitest（単体・シナリオ・シミュレーションのテスト） | ルールの中核のテストはNode.jsだけで動かせる |
| 配布 | ブラウザ版から始めて、必要になったらデスクトップアプリに包む | 9章で決定していただく |

**この構成を推奨する、本作に固有の理由**
1. **本作の難しさは描画ではなく、計算の正しさにある。**相互作用が38種類以上、対策が24項目ある。ルールの部分をエンジンから切り離せば、ビルドのDPSのシミュレーションや、ツリーの組み合わせのランダムなテストを、描画なしで大量に回せる（7章のテスト方針の前提）
2. **コンテンツの量が多い**（ノードだけで約2,000）。型とスキーマで、データの誤り（存在しないタグの参照、上限のない乗算など）を読み込むときに機械的に検出できる
3. **AIによるコード生成で作業を進める**前提なので、学習データが最も多く、型の検査で生成の誤りを早く見つけられる言語が向いている
4. **2Dの見下ろし型ARPGに必要な描画性能**（数百の敵と投射物）は、Phaserで十分に出せる。性能が足りない部分（大量の投射物）だけを、使い回しや一括描画で最適化する
5. Phaserの物理演算は使わず、**当たり判定（円・矩形）はルールの中核で自作する**。そうすれば計算が再現可能になり、シミュレーションとゲーム本体の結果が一致する

**この構成の弱点と対策**
| 弱点 | 対策 |
|---|---|
| Godot・Unityのような視覚的なエディタがない | マップはタイルマップエディタ、データはJSONとスキーマで編集する。デバッグ用の画面（当たり判定の表示、修正値の内訳の表示）を最初に作る |
| ブラウザで動かすと、セーブの保存先に制約がある | セーブは「保存先」を差し替えられる形にする（ブラウザのストレージ／デスクトップのファイル） |
| エンジンのメジャーバージョンが変わる可能性 | 表示層をルールの中核から切り離しているので、表示層だけを差し替えればよい |

### 3.4 JavaScriptではなくTypeScriptを選ぶ理由

- 効果の定義・修正値・タグ・セーブデータは形が複雑で、数が多い。JavaScriptでは、形の誤りが**実際にその効果が発動するまで**見つからない
- TypeScriptはJavaScriptと同じ実行環境で動き、ライブラリもそのまま使える。JavaScriptを選んで得られる利点は、ほとんどない

## 4. MVPの定義

### 4.1 MVPの目標

> **「装備を拾い、ビルドを変え、強敵に挑む」の一巡りが、本作らしい相互作用を伴って成り立つこと**

MVPの完成の条件（体験の面）：
1. 2つのジョブで、**操作の感触が明らかに違う**（同じ敵を、違うリズムで倒す）
2. 拾った装備（特にユニーク）がきっかけで、**ツリーの取り方を変えたくなる**場面がある
3. 第1章のボスに対して、**まったく違う3つ以上のビルドで勝てる**
4. 振り直しとロードアウトで、**ビルドを試す・戻すが苦にならない**
5. ボスの周回に意味がある（討伐証、専用ドロップ、クラフトの素材）

### 4.2 MVPの範囲の推奨案

| 項目 | 推奨案 | 理由 |
|---|---|---|
| ジョブ | **戦士＋盗賊**（9章で選択肢を比較） | ①どちらも武器のダメージで戦うので、C-02（呪文・召喚物の成長が未定義）に依存しない ②仕様書の第1章（獣、腐根の母樹＝毒と出血の入門、千の小傷）と内容が合う ③「重い一撃と崩し」対「背面・連撃・状態異常」で、操作の感触がはっきり違う |
| 地域 | 第1章（森）＋第1章のボス「腐根の母樹」 | 仕様書12章 #9 の案と同じ |
| キャラLvの上限 | **20**（9章で選択肢を比較） | 転職神殿（Lv15）を含められる。詞のtierはT7（iLv1）とT6（iLv12）になる |
| 星辰盤 | **剛域・剛迅域・迅域の一部**（約120〜150ノード） | 戦士（剛）と盗賊（迅）の始点と、その間の領域。天極は K01 血の盟約・K10 重荷の誇り（剛域）、K09 徒手の極意（剛迅域）、K12 千変・K15 影写し（迅域）を候補にする |
| 職紋盤 | 両ジョブの基本職の部分（ただし45ノードのうち、MVPで実装するのは一部）＋職奥義3つずつ | 仕様書には一部のノードしか書かれていないので、残りのノードの定義が必要（H-12と同じく、追加の定義を承認していただく） |

### 4.4 MVPでは後回しにする機能

**後回しにしても、拡張できなくなる簡易な作りにはしない。**右の列は、MVPの時点で用意しておくもの。

| 後回しにする機能 | 理由 | MVPの時点で用意しておくこと |
|---|---|---|
| 騎士・魔法使い・召喚士・弓使い | H-05・H-09・C-02・H-03の解決が前提 | ゲージ・技・ジョブのデータの形を汎用にしておく。**3つ目のジョブを、本体を変えずにデータとルールフックだけで追加できるか**を、MVPの完成の条件に含める |
| 上位職・混成職 | 詳細が未定義（M-01、M-02） | ジョブの定義に「上位職」「元のジョブ」の項目を持たせる |
| サブジョブ | キャラLv25で開く（MVPの上限より上） | 修正値の出どころに「サブジョブ」の種類を用意し、簡易動作（5.1）の規則をデータで持てるようにする |
| 流派盤 | 武器熟練の経験値が未定義 | ツリーの仕組みを「複数のツリー」に対応させておく（星辰盤と職紋盤で、すでに2種類を扱う） |
| セット装備と縁 | MVPの範囲の部位・Lvでは揃わない | 効果の条件に「装備している数」を数える種類を用意しておく |
| 星刻品・星詞 | iLv60以上 | レアリティをデータで追加できるようにしておく |
| 遺物 | キャラLv20で開く。写し取る小星の選び方が未定義（M-12） | ノードの「取得済みとして扱う」状態を、休眠の規則（C-04）と一緒に設計しておく |
| 残響・共鳴座 | H-08の解決が前提 | ユニークの効果を「装備の外」から発動できる形（効果の出どころを差し替えられる形）にしておく |
| 再鍛・詞片の書庫・刻詞の筆・抽詞の針・星刻の灯・昇詞の鎚 | 中盤以降の要素 | 装備の実体に「iLv」「鍛造負荷」「付与の履歴」を持たせておく |
| 試し打ちの場（無料で試す） | 「仮の状態」の実装コストが大きい（M-22） | ルールの中核を「状態をまるごと複製できる」形にしておく（シミュレーションにも必要） |
| 第2章以降、回廊、季節 | 範囲外 | ドロップ表・敵・地域をデータで追加できるようにしておく |
| ゲームパッド | 初期版はキーボード・マウス | 入力の抽象化（行動の割り当て）を最初から作る |

## 5. 開発工程表

### 5.1 工程の順序を決めた理由

本作では、全ての相互作用が「**タグ → 効果 → 修正値の集計 → ダメージ計算**」という一本の流れの上に乗る。そのため、

1. **ルールの中核（描画なし）を先に作り、自動テストで固める。**ここが揺れると、後の全ての工程で手戻りが起きる
2. **画面の上で「殴れる」状態を早く作る。**操作の感触（回避・ヒットの手応え）は、数値より先に確かめる必要がある
3. **装備とツリーは、ジョブと敵の後に作る。**装備とツリーは「何を強化するか」の対象（技・ゲージ・敵）が先にないと、効果を確かめられない
4. **セーブは、保存する対象（アイテム）ができた直後に作る。**後回しにすると、データの形を後から変えにくくなる
5. **バランス調整は最後に行う。ただし、調整のための道具（DPSのシミュレーター）は早い段階で作る**

### 5.2 系統の分類

| 記号 | 系統 | 含まれる工程 |
|---|---|---|
| F | 基盤システム | F-1、F-2、F-3 |
| BT | 戦闘システム | BT-1、BT-2 |
| EQ | 装備・ドロップシステム | EQ-1、EQ-2、EQ-3 |
| JS | ジョブ・スキルシステム | JS-1、JS-2 |
| TR | スキルツリー | TR-1、TR-2 |
| UI | UI | UI-1、UI-2（簡易な表示はBT-2・JS-1に含める） |
| DG | ダンジョン・敵・ボス | DG-1、DG-2 |
| SV | セーブ・ロード | SV-1（データの形の決まりはF-2で先に作る） |
| BL | バランス調整 | BL-1（道具）、BL-2（調整） |

### 5.3 工程の流れと依存関係

```
P0 準備（決定・仕様の修正・周辺仕様書）
 │
F-1 プロジェクトの基盤 ─→ F-2 データの基盤 ─→ F-3 効果・タグの仕組み
                                               │
                              BT-1 ダメージ・状態異常の計算（描画なし）
                                 │            └─→ BL-1 DPSシミュレーター
                              BT-2 戦闘の実体（移動・回避・当たり判定）
                                 │
                     ┌─────────┼──────────┐
                  JS-1 戦士          DG-1 敵の基盤と獣系の敵
                     │                   │
                  JS-2 盗賊・転職 ←──────┘
                     │
                  EQ-1 アイテムの生成・ドロップ
                     │
                  UI-1 インベントリ・装備・ツールチップ
                     │
                  SV-1 セーブ・ロード
                     │
                  TR-1 星辰盤 ─→ TR-2 職紋盤 ─→ EQ-2 ユニーク・潜在効果
                     │
                  EQ-3 強化・クラフト
                     │
                  DG-2 第1章・ボス・討伐証
                     │
                  UI-2 ロードアウト・振り直し
                     │
                  BL-2 バランス調整
                     │
                  MVP 統合テスト・完成の判定
```

並行して進められるもの：JS-1とDG-1、TR-1の画面（UI）とEQ-3、BL-1は BT-1の後ならいつでも拡張できる。

### 5.4 区切り（マイルストーン）

| 区切り | 到達する工程 | 遊べる内容 |
|---|---|---|
| M1「計算が正しい」 | F-3、BT-1、BL-1 | 画面はないが、ダメージ・状態異常・修正値の計算がテストで保証される |
| M2「殴れる」 | BT-2、JS-1、DG-1 | 戦士で獣と戦える |
| M3「拾える」 | JS-2、EQ-1、UI-1、SV-1 | 2ジョブで戦い、装備を拾って着替え、セーブできる |
| M4「育てる」 | TR-1、TR-2、EQ-2、EQ-3 | ツリーとユニークでビルドを組める |
| M5「挑む」＝MVP | DG-2、UI-2、BL-2 | 第1章のボスに、違うビルドで挑戦できる |

## 6. データ設計方針

### 6.1 原則

| # | 原則 | 理由 |
|---|---|---|
| 1 | **コンテンツはデータ、仕組みはコード**。数値・タグ・条件・効果の組み合わせはデータで持つ。ゲームのルールを変える効果は、本体に「ルールフック」として登録し、データから名前とパラメータで呼び出す | 本体を変えずにコンテンツを追加・変更できる |
| 2 | **IDは一度決めたら変えない**。表示名は別に持つ | 仕様書10.2節。セーブデータの互換性 |
| 3 | **装備の実体は「抽選の結果」だけを保存し、能力値は読み込むたびに計算し直す** | データの数値を変えたとき、既存の装備にも反映される（仕様書10.2節「ユニークは新しい仕様に置き換える」） |
| 4 | **全ての効果に「打撃値・基準値への影響」「効く範囲」を必須の項目として持たせる** | V-07、H-08、C-03の問題を、データの形で防ぐ |
| 5 | **未定義の値は「仮」の印を付けて置く** | 仕様の決定を待つ間も実装を進められ、「仮」の値の一覧を自動で出せる |

## 7. テスト方針

### 7.1 基本の考え方

- **ルールの中核（描画なし）を自動テストの中心に置く。**相互作用の正しさは、画面を見て確かめるには組み合わせが多すぎる
- テストは「①1つの式が正しいか」「②2つ以上の要素を組み合わせたときに正しいか」「③ランダムな組み合わせでも、決して破れない性質（不変条件）が保たれるか」「④ビルド全体として目標の範囲に入るか」の4層で作る
- **仕様書の数値の例・相互作用の表（I-01〜I-38）・対策の表（V-01〜V-24）を、そのままテストの項目にする。**仕様書とテストが一対一で対応すれば、仕様の変更がテストの変更として残る
- 乱数は全てシードを指定して動かし、失敗を再現できるようにする

### 7.2 テストの種類

| # | 種類 | 内容 | 例（期待する結果） | 実施する工程 |
|---|---|---|---|---|
| T1 | ダメージ計算の単体テスト | 2.4・2.6の式、加算と乗算の区別、上限 | 防具値1,000で物理ダメージ200を受ける → 軽減率 1,000÷(1,000＋2,000) ＝ 33.3%／防具値がいくら高くても軽減率は85%まで／耐性は75%まで（効果で90%まで）／「物理+30%」と「近接+20%」→ +50%（加算） | BT-1 |
| T2 | タグ条件の適用テスト | タグの照合、親タグ、条件の組み合わせ（全て・いずれか） | 刃の門：長剣・大剣で開き、短剣では閉じる／`[投射][氷]`の条件は、投射で氷の技にだけ効く | F-3 |
| T3 | 効果の優先順位のテスト | H-07で決めた規則 | 「必ず会心」と「会心しない」が両方あるとき、決めた規則どおりの結果になる | F-3 |
| T4 | 属性の変換の多重適用を防ぐテスト | ランダムな変換の組み合わせを大量に生成 | 変換の合計は100%を超えない／下流から上流には変換されない／聖からは変換されない／同じ補正が二重にかからない／付け替えと変換が混ざらない | BT-1 |
| T5 | 状態異常のテスト | 付与、重ね掛け、持続、ボスへの効果、基準値 | 出血は最大8スタック（千の小傷で12）／燃焼は重ね掛けされず最も強い1つが残る／ボスの凍結は0.4秒、その後8秒は凍結しない／基準値への影響が `affects` の項目どおり（V-07） | BT-1 |
| T6 | 装備と技の相互作用のテスト | 武器による技の変化、適性、武具連携 | 連刃：短剣で3連撃、爪で4連撃と出血、片手剣で2連撃の範囲攻撃／適性Sで攻撃速度+10%、Cで-10% | JS-1、JS-2 |

| T8 | サブジョブとの相互作用のテスト（MVPの後） | 簡易動作（5.1）、適性の決め方 | サブジョブの召喚技は契約枠6で固定／適性はメインとサブ（1段階下げたもの）の高い方／混成職のときはサブジョブを設定できない | MVPの後（テストの項目は先に作っておく） |
| T9 | スキルツリーの効果の検証テスト | ランダムなノードの取得・返却、装備の着脱を繰り返す | 有効なノードは全て始点につながっている／使ったポイントは上限以下／**同じ状態で2回評価すると、結果が同じ**（C-04）／条件の判定に循環がない／休眠したノードは、条件を満たすと元に戻る | TR-1、TR-2 |
| T10 | 相互作用の回帰テスト | I-01〜I-38、V-01〜V-24 を1つずつシナリオにする | V-01：同じユニークを装備と残響で同時に使えない／V-14：孤独の指輪で蟻塚の指輪の上限は30%のまま／V-18：徒手の極意は副手の片手武器を2倍にしない／I-30：千の小傷＋毒血同源で、出血が毒として数えられる | 各工程（MVPの範囲から先に） |

### 7.3 テストを回すタイミング

| タイミング | 実行するテスト |
|---|---|
| 変更のたびに（自動） | T1〜T7、T9〜T11、T13、T17 |
| データ（数値）を変更したとき | 上に加えてT14（DPS比較）。結果を前回と比べ、大きく変わったビルドを報告する |
| 区切り（M1〜M5）ごと | 全てのテスト＋T16（性能）＋プレイテスト |

### 7.4 プレイテストで確かめること（自動テストでは分からないこと）

| 観点 | 確かめること |
|---|---|
| 成長の実感 | 最初の10分で、新しい技か装備を手に入れられるか |
| 収集の動機 | 「？？？」の潜在効果を見て、条件を試したくなるか |
| ビルドを試す楽しさ | 振り直しの費用や手間が、試すことのじゃまになっていないか |

| 周回 | ボスを2回目に倒すとき、また挑む理由を感じるか |

| R-01 | **コンテンツの量**（ノード約2,000、ユニーク、詞、技）が、制作の能力を超える | 高 | 大 | MVPは約150ノードに絞る。ノードは「型」から量産できる形にする（小星の型、星座の型）。全体の規模は、MVPの後で見直す |
| R-02 | **相互作用の組み合わせの爆発**で、想定外の強すぎる組み合わせが見つかる | 高 | 大 | 乗算を持てる出どころをデータの段階で制限する（T17）。DPSのシミュレーションを毎回回す（T14）。突出したビルドは、数値の調整か仕様の修正として扱う |
| R-03 | **仕様の未定義の部分**（Critical・High）が実装中に見つかり、手戻りが起きる | 高 | 大 | P0で決める。決まっていない値は「仮」の印を付けて進め、一覧を自動で出す |
| R-04 | **ルールの中核と表示層の結合**が進み、テストとシミュレーションができなくなる | 中 | 大 | ルールの中核が表示層のライブラリを参照していないことを、自動で検査する |
| R-05 | **星辰盤の画面**が大きすぎて、操作しにくい・重い | 中 | 中 | TR-1で早めに試作し、ユーザーに確かめていただく。検索・タグの強調・拡大縮小を最初から入れる |
| R-06 | **ドット絵の制作量**（8方向 × ジョブ × 武器 × 動き） | 高 | 大 | MVPは仮の素材で作る。装備の見た目をキャラクターに反映するか（9章）で、量が大きく変わる |
| R-07 | **投射物の数**（分裂の重ね掛け）による性能の低下 | 中 | 中 | 使い回しと一括描画。性能テスト（T16）。必要なら投射物の数の上限（M-21）を仕様として決めていただく |
| R-08 | **セーブデータの移行**の失敗で、データが失われる | 低 | 大 | 版の番号、移行のテスト、読み込みの前に元のファイルを残す |
| R-09 | **AIが生成したコードの一貫性**（同じ処理が別々に書かれる、決めた規則から外れる） | 中 | 中 | 共通の仕組み（効果・修正値・ルールフック）を先に作り、それ以外の方法での実装を禁止する規則を、プロジェクトの説明書きに書く。データの検証とテストで、規則から外れたものを検出する |
| R-10 | **仕様と実装のずれ**（実装中に、仕様にない判断が積み重なる） | 中 | 中 | 実装中に見つかった曖昧な点は、その場で決めずに一覧にし、まとめて承認していただく（今回の方針と同じ） |
| R-11 | **周辺仕様書（敵・ボス・ダンジョン）の不足**で、MVPの「遊び」が成り立たない | 中 | 大 | P0で周辺仕様書を作る。DG-1の段階で敵の行動の手応えを確かめる |
| R-12 | **ブラウザでの配布の制約**（保存先の容量、全画面、入力の遅延） | 低 | 中 | 保存先を差し替えられる形にする。必要ならデスクトップアプリに包む（9章） |

## 9. 開発開始前に決める必要がある事項（選択肢とメリット・デメリット）

### 9.1 実装を始める前に、必ず決めていただく事項

#### D-01 Criticalの修正方針（C-01〜C-04）
詳しい内容は2.1節。それぞれ、推奨案で良いか、代替案にするかを決めていただきます。

| 項目 | 推奨案 | 代替案 |
|---|---|---|
| C-01 基礎性能の範囲 | 基礎ダメージと防御値（防具値・回避値・魔障）だけ | ガード率も含め、上限を新しく設ける |
| C-02 技・呪文・召喚物の成長 | 技レベルの仕組みを定義する | キャラLvに連動させる／呪文用の追加ダメージの詞を作る |
| C-03 状態異常の計算 | 総量の表記に揃え、基準値は会心・耐性・防御を含めない。持続ダメージは耐性で1回だけ軽減する | 基準値に会心を含める（持続ダメージが実質的に会心する） |
| C-04 ツリーの評価順序 | 3段階の評価＋休眠の規則の統一＋遺物の写しは経路に使えない | 遺物の写しを経路に使える |

#### D-02 MVPのジョブ

| 選択肢 | メリット | デメリット |
|---|---|---|
| **A：戦士＋盗賊（推奨）** | 武器のダメージで戦うのでC-02に依存しない。第1章の内容（出血・毒・千の小傷）と合う。重い一撃と連撃・状態異常で、感触がはっきり違う | どちらも近接が中心。遠距離の遊び（呪文・矢）を確かめられない |
| B：戦士＋魔法使い | 近接と遠距離の対比が大きい | C-02・H-09の解決が前提で、P0の作業が増える。第1章のボスのユニーク（千の小傷）が活きない |
| C：戦士＋盗賊＋魔法使い | 遊びの幅が最も広い | MVPの規模が約1.5倍。完成までが遠くなる |

#### D-03 MVPのキャラLvの上限

| 選択肢 | メリット | デメリット |
|---|---|---|
| 15 | 最も小さい。第1章の範囲（Lv1〜15）と一致 | 転職神殿（Lv15）がちょうど開くだけで、2つ目のジョブを育てる時間がない。U06（Lv20）が入らない |
| **20（推奨）** | 転職を試せる。U06が入る。詞はT7・T6 | 中級のベース（Lv25）、T5の詞は入らない |
| 25 | 中級のベースとT5の詞が入り、装備の成長を感じやすい | サブジョブ（Lv25）が開く時点なので、サブジョブを入れるかの判断が必要。地域のコンテンツが多く要る |
| 30 | サブジョブ・遺物まで含められる | 第2章の内容が必要になり、MVPの範囲が大きく広がる |

#### D-04 技術スタック

| 選択肢 | メリット | デメリット |
|---|---|---|
| **A：TypeScript＋Phaser（推奨）** | ルールを描画なしでテスト・シミュレーションできる。AIによるコード生成と型の検査の相性が良い。この環境でエディタなしで開発できる | 視覚的なエディタがない。PC向けの配布には、デスクトップアプリに包む手間がある |
| B：TypeScript＋PixiJS（描画のみ）＋自作 | 描画が軽く、構成を自由に決められる | シーン・入力・音などを自作する必要があり、初期の工数が増える |
| C：Godot 4 | 2Dの機能とエディタが強力。PC向けの書き出しが標準 | エディタでの作業が前提になる部分が多く、この環境での開発に向かない。ルールの部分を描画なしで大量に回すテストがしにくい |

#### D-05 配布の形

| 選択肢 | メリット | デメリット |
|---|---|---|
| ブラウザ版だけ | 最も手軽。確認がすぐできる | セーブの容量・全画面・入力の扱いに制約。PCのゲームとしての販売には向かない |
| デスクトップアプリだけ | PCのゲームとして自然。ファイルに保存できる | 確認のたびにビルドが必要 |
| **開発中はブラウザ、配布はデスクトップアプリ（推奨）** | 開発の速さと、配布の自然さを両立できる | 保存先などを差し替える仕組みが必要（3.3節で対応済み） |

#### D-06 移動と照準の操作（仕様書は「8方向に移動」とだけ定めている）

| 選択肢 | メリット | デメリット |
|---|---|---|
| A：キーボードで移動＋マウスで照準 | 8方向の移動と自然に合う。ゲームパッドの「左スティックで移動・右スティックで照準」にそのまま対応できる | 両手を使う操作になる |
| B：クリックで移動 | 見下ろし型ARPGでよくある操作 | 回避・パリィ（0.18秒）のような精密な操作と合わせにくい。ゲームパッドへの対応で作り直しが必要 |
| C：AとBの両方を設定で選べる | 好みに合わせられる | 実装とテストの量が2倍 |

照準の方向を「自由な角度」にするか「8方向に限る」かも決めていただく必要がある（ドット絵の向きの数に関係する）。

#### D-07 ダンジョンの構造（仕様書に定義がない）

| 選択肢 | メリット | デメリット |
|---|---|---|
| 固定のマップ | 作り込める。隠し部屋（隠し星）を置きやすい | 周回すると飽きやすい |
| 自動で生成する | 周回の変化が大きい | 生成の仕組みの実装コストが大きい。質を保つのが難しい |
| 固定の地形＋敵・宝箱の配置がランダム | 中間の手間で、周回に変化が出る | 地形の変化はない |

#### D-08 周辺仕様書（敵・ボス・ダンジョン・町・経験値・金貨・薬瓶・死亡時の扱い）の作り方

| 選択肢 | メリット | デメリット |
|---|---|---|
| **A：私が草案を作り、ユーザーが承認する（推奨）** | 早い。本仕様書と用語・形式を揃えられる | 承認の手間がかかる |
| B：ユーザーが作る | 意図どおりになる | 作業の負担が大きい |

#### D-09 MVPのユニーク

| 選択肢 | メリット | デメリット |
|---|---|---|
| A：仕様書のもの（U02・U03・U06）だけ | 仕様の追加がない | 「ユニークによる特殊なビルド」の幅が狭い。第1章のボスの交換候補が実質1つ（樹皮の盾は効果が未定義、蛇使いの骨笛は遺物でMVPの範囲外） |
| B：MVPの範囲で使えるユニークを追加で設計し、承認していただく | ビルドの幅が広がり、MVPの目標（4.1の条件2・3）を確かめやすい | 仕様の追加になる。設計と承認の手間 |

#### D-10 ドット絵の方針

| 決めること | 選択肢 | 考慮すること |
|---|---|---|
| 素材 | 仮の素材で作り、後で差し替える／最初から本番の素材で作る | 仮の素材なら、仕組みの検証を先に進められる |
| タイルの大きさ・画面の解像度 | 例：16ピクセル／32ピクセル | 表現の細かさと、制作量の兼ね合い |
| 装備の見た目をキャラクターに反映するか | する／武器だけ反映する／しない | 反映すると、8方向×動き×装備の数だけ素材が必要になる（R-06） |

#### D-11 死亡したときの扱い（仕様書に定義がない）

ゲームの緊張感と、試行錯誤のしやすさに直接影響します。選択肢の例：経験値の一部を失う／金貨の一部を失う／失うものはなく町に戻るだけ／難易度ごとに選べる。いずれも仕様の追加になるので、方向性を決めていただきます。

|---|---|---|---|
